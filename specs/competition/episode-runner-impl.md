## 1. Competition images<a id='images'></a>

Implements `episodes.md` §3.4 (competition image).

The competition's additional override file, `competition/deploy/override.yaml`, sets the compression factor (`episodes.md` §5.2, the compression factor).

The competition's additional override file also gives `siem-01` the build-script template `siem-01-competition.sh.j2`, in the template directory `competition/deploy/build-scripts/`, and the image name `ravensport/siem-01-competition:latest`. The template extends `deploy/build-scripts/siem-01.sh.j2` through Jinja blocks, which add the idle defender, as the program `/usr/local/bin/idle-defender`, and the query interface before the image is published. The template also installs the launcher, `/usr/local/bin/defender`, a shell script that the step session runs (`episodes.md` §7, step protocol).

Before it opens the step session, the episode runner tests `/var/lib/entry/defender` through an `incus exec` of its own into `siem-01`. A regular file that `siem-01` can read and execute gives the entry's program, `/var/lib/entry/defender`, and an empty path the idle defender's program, `/usr/local/bin/idle-defender`. A volume that `siem-01` cannot read and search, and a path that holds anything else, each discard the episode (`episodes.md` §12, terminated and discarded episodes). The episode record's cause is `the entry's defender cannot run: ` followed by the test's message. The messages are `/var/lib/entry cannot be read and searched` and, for the path, `/var/lib/entry/defender is not readable`, `is not executable`, `is a directory`, `is a symbolic link to nothing` or `is not a regular file`. The episode's file in the episode record holds the tested program under the key `defender_program`.

The step session is `incus exec siem-01 -- /usr/local/bin/defender PROGRAM`, with the tested program as its argument and no option for the user, so the program runs as root. The launcher sets the working directory with `cd /root`, and tests the volume and the path again in the same way. When its own test gives `PROGRAM`, the launcher replaces itself with `PROGRAM` through the shell's `exec`. At a fault, or when the two tests differ, the launcher writes the cause to its standard error after `launcher: `, and exits with status 126 running no program. The record therefore names only a program that ran. Called without an argument, the launcher writes `launcher: no program named, which the episode runner tests first` and exits with status 2. When `cd /root` fails, the launcher exits with status 1. The program that replaces the launcher holds the step session's standard input and standard output, and its exit ends the step session.

The competition's additional override file also sets four flow timeouts of packet inspection on the three firewall nodes (`episodes.md` §5.3, timings; `siem.md` §4.2, flow records). The flow timeouts change the images of the firewall nodes. The competition's additional override file therefore also gives each of the three firewall nodes a competition firewall image with an image name of its own, such as `ravensport/fw-ot-dmz-competition:latest`. `render.py` passes the flow timeouts to the build script of each firewall node's operational image. The same build script builds the competition firewall image too, and writes the flow timeouts into its configuration of Suricata, the packet inspection software. Without an additional override file that sets flow timeouts, the firewall nodes keep Suricata's packaged flow timeouts. `render.py` refuses an additional override file that sets a flow timeout and leaves a firewall node with its operational image name.

The competition's additional override file also gives `sim-host` a competition image, `ravensport/sim-competition:latest`. The script that builds the operational image of `sim-host`, `deploy/scripts/build-sim-image.sh`, builds the competition image too (`deployment.md` §6.2, sim-host image). The competition's entry point is the crate `competition/sim/`, which depends on the simulator's crate `infra/sim/`. Every parameter of the simulator that the start-up input leaves out takes the value that the simulator's own binary gives it. The build of the competition image sets `SIM_CONSTANTS` to `build/sim/sim-constants.toml`, the constants that `render.py` scales by the compression factor, so the image compiles the simulator against them (`deployment-config.md` §4.1, sim projection). The image's input hash covers both crates and those constants, so a change of the compression factor alone rebuilds the image. The image also holds the empty directory `/var/lib/sim/startup`, where the start-up input is mounted.

The competition's additional override file neither adds nor patches the node `adversary`, so the adversary host of every living port runs from its own image (`episodes.md` §6.5, adversary host). The episode runner reads the attack chains' catalogue, `attack-chains/dist/chains.json`, with `schema_version` 2, which the attack chains' generator writes when `make build-attacks` in `deploy/` runs it (`episodes.md` §10.1, the competition library).

**An entry's override file.** An entry that gives its own images names each of them in its own version of the competition's additional override file (`episodes.md` §3.2, modes). The entry generates that file from `competition/deploy/override.yaml` at each build, so the file differs from the competition's only where the entry's patch changes it. The patch changes no part of the adversary host's node definition. The template of each of the entry's images extends the build-script template of the image that the host would otherwise run. The entry's image of `siem-01` therefore extends `siem-01-competition.sh.j2`, and keeps the launcher, the idle defender and the query interface. The episode runner's commands `run` and `copy`, and the living port's manager's command `create`, take the entry's file with the option `--extra-override FILE`. The option takes its name from `render.py`'s option and the Makefile's variable `EXTRA_OVERRIDE`, and without it each command takes `competition/deploy/override.yaml`. At fork 0, `run` passes the file to `make` as `EXTRA_OVERRIDE` as it deploys, and reads the compression factor and the timings from it. `copy`, which deploys nothing, reads the compression factor from the file. `create` checks that the tree holds the file, passes the file's path in the tree to the guest's render, build and deployment, and records the path in the living port's record.

## 2. Start-up input<a id='startup'></a>

Implements `episodes.md` §4.3 (start-up input).

Every user may read `startup.json`, because its owner on the Incus host lies outside the range of users that the unprivileged container maps (`sim-network.md` §8, hardening). `startup.json` is a JavaScript Object Notation (JSON) object with exactly the two fields below. Each field sets the simulator's parameter in its row (`sim-impl.md`, "Start state"). Beside the simulator's `WARN` and `ERROR` events, the entry point's log filter admits every `INFO` event of three sources, which the simulator's default filter of `WARN` would hold back (`sim-impl.md`, "Logging"). The entry point logs one, `start_state`. The tug arrival generator logs each tug's scheduled arrival and each tug's arrival. The fuel supplier logs each poll, each order it places, each road tanker's arrival and the end of each delivery. The episode runner reads all of them apart from the tugs' arrivals, since a tug arrives at its logged scheduled arrival. The polls' times come from the tank-gauge relay's journal, which the episode runner checks against the logged polls (`episodes.md` §6.4, how a fork is made).

| Field | Value | Parameter | At a living port's start |
|---|---|---|---|
| `sim_tug_arrivals` | The seed of the generator `sim_tug_arrivals`, an integer from 0 to 2^64 − 1 | The tug arrival generator's `seed` | The living port's tug seed (`episodes.md` §4.2, derivation) |
| `next_audit_at` | The time of the first audit, such as `2026-11-10T09:30:00Z` | `first_audit_after`, the time from the start to `next_audit_at` | One compressed audit period and one compressed audit settling delay after the episode runner writes the start-up input |

Every other parameter of the start state takes the simulator's default (`sim-impl.md`, "Start state"). The tank holds 35,000 litres, no order is placed, both totalisers read zero, and every tug is away from the dock. The first bunker delivery note and the first delivery ticket are numbered 1. The fuel supplier's first poll and the systems administrator's first routine check come one compressed interval after the simulator's start. The reconciliation user holds no paper from before the simulator's start. The first audit's window therefore runs from the simulator's start to one compressed audit period after the episode runner writes the start-up input (`sim-impl.md`, "Reconciliation user").

## 3. Scan requests<a id='scan-requests'></a>

Implements `episodes.md` §6.2 (first occurrences).

For each monitored host, the seed of the generator `wazuh_first_file_integrity_scan/` followed by the host's name, such as `wazuh_first_file_integrity_scan/fms-01`, divided by 2^64, gives a fraction of at least 0 and less than 1. The time of the host's first file-integrity scan is that fraction of the file-integrity scan's compressed interval after the simulator's start. A host added to the monitored set therefore leaves the times of the other hosts' first file-integrity scans unchanged.

The Wazuh manager's command-line tool `agent_control`, with its option `-r`, requests a scan from one Wazuh agent, which runs the scan at its next check-in with the Wazuh manager. The episode runner runs the tool through an `incus exec` of its own into `siem-01`, apart from the step session.

## 4. Living ports<a id='living-ports'></a>

Implements `episodes.md` §6.3 (the living port).

The episode runner makes each fork from the machine that runs the Incus hosts, and runs each episode on the episode's Incus host (`episodes.md` §2, terms). When it creates a living port, the episode runner writes the start-up input of §2 (start-up input) and deploys the living port as `episodes.md` §3.3 (reset) states. In evaluation mode, the episode runner attaches the entry's submitted storage volume read-only to the living port's `siem-01` as it deploys the living port (`episodes.md` §3.2, modes; `general-deployment.md` §1.3, competition profile). The command `run`, which runs one episode at fork 0, takes the submitted volume with `--volume DIR` and attaches it read-only at `/var/lib/entry` in the same way. Before any episode, the command opens the directory's files to `siem-01`'s users, as §5 (forks) states, and fails with the message `the volume DIR cannot be opened: ` and the error when it cannot.

**Updates.** Before it deploys a living port, the episode runner stops and masks the daily timers of the Advanced Package Tool and the service `unattended-upgrades` in the living port's Incus host. An upgrade can restart the Incus service, which ends the step session and makes the reset fail.

**Fork instants.** A living port that makes forks runs no episode at fork 0. The generator `fork_wait` draws one fork wait for each fork, in turn, uniformly from 0 to 6 minutes. On the living port's clock, fork 1 occurs its fork wait after the end of the living port's settle period. Each later fork occurs 14 minutes and its fork wait after the fork before it.

**Seeds.** Before each fork, the episode runner computes the fork's episode seed. When it creates a living port, the episode runner also computes the living port's tug seed, for the start-up input, and the seed of its generator `fork_wait` (`episodes.md` §4.2, derivation).

**Snapshots.** The episode runner takes each snapshot of the schedule in `episodes.md` §6.3 (the living port) by the save that makes a fork (§5, forks). The snapshot cache keeps each snapshot with the living port seed and the snapshot's instant. After each snapshot, the episode runner deletes the oldest snapshots until the remaining snapshots fit the snapshot cache. With a snapshot cache too small for one snapshot, the episode runner takes no snapshot.

**Replay.** For a replay of fork k, the episode runner restores the latest snapshot before fork k's instant on an Incus host of its own. The restored living port runs until fork k's instant, and the episode runner then makes fork k from it. With no snapshot before that instant, the replay starts a new living port with the same living port seed.

## 5. Forks<a id='forks'></a>

Implements `episodes.md` §6.4 (how a fork is made).

Each fork runs on an Incus host of its own, a virtual machine on the machine that runs the Incus hosts. The zone networks lie inside each Incus host, so a fork's zone networks reuse the living port's addresses without conflict. The machine gives each Incus host a network of its own, so a fork also keeps the living port's own address without conflict.

**Making a fork.** The living port's Incus host mounts no directory of the machine that runs it, so a saved state holds no open share, and no fork writes to the machine's files. The episode runner pauses the living port's Incus host for every save, on every platform, since the hypervisor on a macOS machine aborts a save of a running virtual machine. Where the machine's file system clones a file without copying its data, the episode runner clones the top image of each disk, so each of the living port's disks keeps one layer above its base. Elsewhere the episode runner switches each disk to a new copy-on-write layer, so the layer beneath stays as it was at the pause. The episode runner then saves the memory and device state to a file, and resumes the living port. Each fork starts from the saved state, with a copy-on-write layer of its own on each disk. Whenever a fork, a replay or a snapshot is deleted, the episode runner merges into the living port's top layer every layer that no running fork, replay or kept snapshot reads. In tests of living ports with 8 gibibytes of memory, each save wrote about 8 gigabytes and paused the living port for 1.5 to 2.4 seconds on a macOS machine with an Apple processor. On a Linux machine a save paused the living port for 1.6 to 2.1 seconds with the state written to memory, and for 5 to 31.4 seconds with it written to disk. Each fork ran 0.7 to 2.6 seconds after the episode runner launched it, and up to 22 seconds when the machine's memory was short. On a macOS machine with an Intel processor, a save paused the living port for 5.5 to 37 seconds, and each fork ran 8.9 to 32 seconds after its launch.

**The volumes of `siem-01`.** Both volumes mount at `/var/lib/entry`, which no option of the episode runner changes. Before it attaches either volume, the episode runner opens each of its files for reading by every user, and for execution by every user where the file's owner may execute it. In evaluation mode, each fork's `siem-01` holds the entry's submitted storage volume read-only, as the living port's does. In training mode, the episode runner keeps every version of the training volume on the machine that runs the Incus hosts, and starts each lineage from a volume that the command line gives. Once the previous episode's reset has kept the training volume's version, the fork starts. The episode runner imports the lineage's latest version into the fork's Incus host, and attaches it read-write to the fork's `siem-01`. The episode runner then confirms the settle conditions, and step 0 follows at once (`episodes.md` §6.6, settle period). At the reset, the episode runner detaches the training volume and exports it as the lineage's next version, before it deletes the fork's Incus host. The episode record names both versions.

**The held clock.** The episode runner stops the time-synchronisation client in each Incus host, and the guest agent of Lima, the manager of the release profile's virtual machine (`general-deployment.md` §1.1, release profile). The clock source of each Incus host must also stop during each pause of the Incus host. In tests on a Linux machine and on a macOS machine with an Apple processor, each living port's clock lagged the machine's clock by the sum of its pauses, within 0.8 seconds. Each fork's clock resumed at the fork instant. On a macOS machine with an Intel processor, the default clock source, the time-stamp counter, keeps counting through a pause and a restore. In tests the time-stamp counter left a gap as long as each pause in the living port's readings, and each fork's clock started at its restore. On a macOS machine with an Intel processor, the episode runner therefore switches the living port's clock source to the high precision event timer as it creates the living port. Every fork keeps that clock source. With the high precision event timer, a save shifted the living port's clock by its pause within 0.02 seconds, and the fork's clock resumed at the fork instant. The living port's processor use at idle rose from 1.1% to 2.8% with that clock source. In a living port created with that clock source, each of 11 saves shifted the clock by its pause within 0.018 seconds.

## 6. Step messages<a id='step-messages'></a>

Implements `episodes.md` §7 (step protocol).

A decision request and the end notice hold the same four keys. The key `track` holds the track as the string `A` or `B`, and `step` holds the step's number, counted from 0. The key `previous_reward` holds the reward computed at the end of the previous step, and `null` at step 0. In evaluation mode, `previous_reward` holds `null` in every decision request and in the end notice. The key `ended` holds `false` in a decision request and `true` in the end notice. The end notice's `step` is the number of steps that the episode ran: T at the horizon, and fewer after a terminal state. A decision message holds one key, `decision`, whose value is the decision, with no action written as the string `no action` in both tracks, and the Track A alarm as `alarm`. A defensive action's string awaits the specification of the defensive actions. A line is a decision message only when it is a JSON object whose one key is `decision` and whose value is a string. Any other line, and a decision message whose decision is not one of the track's, is an invalid line (`episodes.md` §7, step protocol). In Track A in training mode, the idle defender answers the decision request `{"track": "A", "step": 7, "previous_reward": 0, "ended": false}` with the decision message `{"decision": "no action"}`, and a defender raises the Track A alarm with `{"decision": "alarm"}`. In Track A in training mode, every decision request after step 0 carries a `previous_reward` of 0, and the end notice carries `R_n`. In evaluation mode the episode record holds `R_n` (`episodes.md` §7, step protocol). In training mode, an alarm that arrives during step 42, after the third of five stages is released, makes the episode runner send the end notice `{"track": "A", "step": 43, "previous_reward": -0.5, "ended": true}` within 1 second of the alarm's arrival.

The episode runner suppresses decisions only when its command line carries the option `--suppressed`, which a replay for Competition Rule 5 gives (`episodes.md` §9, suppressed episodes for Competition Rule 5). Without the option, the episode runner carries out each decision in either mode.

## 7. Targets of stages<a id='targets'></a>

Implements `episodes.md` §10.1 (the competition library).

The first of the following rules that applies decides each stage's target. The first rule takes the one host with a required service. The second takes the one host with a required address, other than a segment gateway. The third takes the one host over which a required capability is held. The fourth takes the required segment, and the last takes the adversary host.

## 8. Ranges of the predicted events<a id='ranges'></a>

Implements `episodes.md` §10.2 (choosing the chain).

In a fork, the episode runner reads each tug's scheduled arrival and requested volume from the simulator's log (`episodes.md` §6.4, how a fork is made). At fork 0 the chain is chosen before anything is deployed, so no log exists (`episodes.md` §3.1, phases). A helper, `competition/predicted_events/`, built against the simulator's crate, then repeats each tug's first draws of its time away and requested volume from the tug seed, on that tug's stream. Every tug starts away from the dock (`sim.md` §2.3, start state), so each tug's first arrival occurs its first time away after the simulator's start. The timings come from the render's projection of `world.yaml` at the competition's compression factor. The episode runner predicts no arrival that follows a departure inside the episode, since the simulator draws a tug's next time away only as the tug leaves the dock.

The dock operator serves the tugs and the road tanker's fill one at a time. Waiting tugs are served in the order they arrived, and a waiting road tanker before any waiting tug (`sim.md` §6, tug arrival generator). The Fuel Management System (FMS) refuses a dispense at its start when the tank's volume less the request is at or below the cavitation threshold (`fms.md` §5.1, the poller of the automatic tank gauge). The episode runner applies that refusal. A refused refuel makes no connections, and the dock operator cancels its job and serves the next at once.

Each range below holds in measurements on a Linux machine, a macOS machine with an Apple processor and a macOS machine with an Intel processor. At fork 0, step 0 begins 65 to 100 seconds after the simulator's start. Step 0 begins the settle delay, 45 seconds, after the last settle condition holds (`episodes.md` §6.6, settle period). In all 17 settle periods measured, condition 2, each Wazuh agent's first file-integrity scan and listening-port inventory, held last, 24.1 to 49.0 seconds after the simulator's start. Four episodes at fork 0, three on the Linux machine and one on the macOS machine with an Apple processor, reached step 0 at 69.1 to 76.9 seconds after the start. The settle periods of 13 living ports, which follow fork 0's procedure, ended at 75.8 to 94.0 seconds after the start. On the macOS machine with an Intel processor, only a living port's settle period was measured, ending at 87.1 seconds after the start. The range starts 4.1 seconds before the earliest step 0 measured and ends 6.0 seconds after the latest end of a settle period.

A refuel's first connection opens 0 to 12 seconds after its tug arrives. The dock operator creates the job on the tug's arrival, and polls the job's status at once and then every 6 seconds at a compression factor of 5 (`sim-impl.md`, "Dock operator"). The dock operator starts the dispense at the first poll that finds the vessel's card validated. The FMS then opens the dispenser connection at its next poll of the dispenser, within 1 second at that compression factor (`fms.md` §5.2, Modbus poller). With a dispense started at the first poll, the first connection can come as early as 0.1 seconds after the arrival, so the range starts at 0 seconds. The range's end, 12 seconds, is one dock operator's poll of a job's status and 6 seconds, and covers a dispense started at the second poll. The one first connection measured directly came 6.43 seconds after the arrival, and 32 estimates, each within about 1 second, gave 0.14 to 0.18 seconds or 6.09 to 6.25 seconds.

The fuel supplier's polls fall due on a fixed schedule: the first poll, then one each poll interval after the previous one fell due (`sim-impl.md`, "Fuel supplier"). A poll's length, its retries and an interception included, delays its own completion and not the later polls. A poll that outlasts the next due time delays that poll, which starts as soon as the slow poll ends, and no poll is skipped. The range of a poll starts 0.3 seconds before its due time and ends 2 seconds after it. The ranges allow 10 seconds for a poll that a stage intercepts, which delays that poll alone. Under the fixed schedule no range widens with the number of intervals since the episode's first poll. A widening for each interval would allow only for drift between the simulator's clock, which schedules the polls, and the clock of the journal from which the episode runner reads them at a fork. Each of 1,198 polls measured made its first connection 1.5 to 38.4 milliseconds after its due time, and a poll's lateness changed by at most 2.2 milliseconds across up to 75 intervals. Each of 57 polls that a stage intercepted ended at most 9.15 seconds after its due time, and the poll after it at most 0.11 seconds after its own.

In a fork, the dock's queue starts with the transfer under way and the tugs waiting at the fork instant. A road tanker may have arrived at the fork instant without its fill having started, during a tug's refuel or before the dock operator creates the fill job. Such a road tanker is in the queue at its arrival time, and is served before any waiting tug. The episode runner learns of it from the simulator's logged arrival of a road tanker with no fill job open in the FMS. The fuel supplier hands the fill to the road tanker driver before it logs the arrival, so a fill opened since the road tanker's scheduled arrival counts as its arrival. The later arrivals are the scheduled arrivals of the tugs away from the dock. With an order pending at the fork instant whose road tanker has not arrived, the later arrivals also hold that road tanker. The road tanker arrives one lead time after the logged poll that placed the order, and is served before any waiting tug (`sim.md` §6, tug arrival generator). The pending order and its road tanker's arrival come from the fuel supplier's logged order (`sim.md` §5.3, fuel supplier), so no ordering poll is ambiguous. An order placed inside the episode brings no road tanker within it, since the lead time, 72 minutes at a compression factor of 5, exceeds the 12-minute horizon. Each poll's time follows from the fuel supplier's next poll at the fork, the first due time on the schedule with neither a connection nor an event. In a fork, the episode runner chooses the chain once the settle conditions hold, so step 0 takes no range. A fork adds a range: the fuel supplier's next poll can come up to 2 seconds late. At the 107 forks measured whose next poll no stage held, that poll came at most 13.0 milliseconds late. The episode runner infers how each procedure under way at the fork instant ends (`episodes.md` §6.4, how a fork is made). A delivery note being linked keeps the dock busy for the link and its retries alone, and a tug or a road tanker that is leaving does not hold the dock. A start state that no procedure under way at the fork instant explains is a fault, which discards the episode. Each inference allows its procedure a bounded time to end, and past the bound the episode runner presumes the inference wrong and discards the episode (`episodes.md` §6.4, how a fork is made). The bounds derive from the dock operator's exchange, provisionally 15 seconds, the 12 seconds of a refuel's start, and the pumping rates at the compression factor. The bounds also derive from the dock operator's poll of a job's status, the 5 seconds allowed for a leaving tug and the lateness of a poll under way. The episode runner groups the relay journal's connections into polls by due time. Each poll takes the connections from the start of its range, 0.3 seconds before its due time, until the start of the next poll's. The connections of a retried poll therefore count as one poll. A poll under way has fallen due, and its event is not in the simulator's log. A poll under way may be more than those 2 seconds and 10 seconds more past its due time, and no more than one poll interval, as when the relay holds its connection without answering. The start state is then uncertain. The episode runner then excludes the poll chains alone. A poll under way more than one poll interval past its due time is a fault, which discards the episode. A road tanker may be past its scheduled arrival by the same margin, with a poll under way that fell due no later than that arrival. The dock's order of service is then uncertain, and the episode runner excludes the refuel chains as well. The 145 forks measured found no poll under way, and no living port's poll stayed under way longer than 24.6 milliseconds. A refuel chain is excluded when a tug leaves the dock inside the episode before the latest start of the refuel that the chain needs (`episodes.md` §10.2, choosing the chain).

## 9. The attack chain's session<a id='session'></a>

Implements `episodes.md` §10.4 (the attack chain's session) and §10.5 (stopping the chain).

The episode runner starts the chain's binary with `incus exec adversary -- sh -c 'echo $$; exec "$0" --paced' /root/<binary>`. The shell prints its process identifier and replaces itself with the binary, so the first line of the session's standard output is the binary's process identifier. The session's standard input and standard output are pipes to the episode runner.

A stage event is one line of JSON whose key `stage_event` is `begin` or `end`. A beginning event also carries `stage_number`, the stage's place in the chain counting from 1, `total_num_stages` and `stage`, the stage's name. An end event carries `stage_number`, `stage` and `outcome`, which is `completed` or `failed`, with `reason` for a failure.

The binary exits with status 0 when every stage completed, 1 at a failed stage or missing facts, and 2 on a command line it cannot use. The binary exits with status 3 when stopped before a stage, and when it cannot write a stage event to its standard output. The termination signal, `SIGTERM`, ends at once a stage that has nothing to restore, and the session then reports the signal's status.

## 10. Export<a id='export'></a>

Implements `episodes.md` §13 (episode record).

The export waits 2 seconds after the end notice, so that the Wazuh manager has written out every line from before the end notice. The Wazuh manager writes each day's records to a dated file of its own (`siem.md` §7, retention). The export copies the dated files of `alerts.json` and `archives.json` of each day from step 0 to the export, on the clock of `siem-01`. The export also copies every earlier dated file that a range in the record of reads names. The export copies only the Wazuh manager's dated files below `alerts/` and `archives/`, and a range that names any other path copies nothing. Each file is copied whole, from its first byte, under its path relative to `/var/ossec/logs/`, and a file that the Wazuh manager has compressed stays compressed. The byte ranges in the record of reads therefore refer to the exported files (§12, query interface). The export leaves out an incomplete line at the end of the current day's files, which the Wazuh manager is still writing. A dated file that the Wazuh manager is compressing at the export is copied as it stands. An output file with no dated file of the episode's days fails the export. A dated file that a range in the record of reads names, and that `siem-01` no longer holds, fails the export, as a dated file that the export cannot copy does. After the export, the episode runner moves the episode record from a fork's Incus host to the machine that runs the Incus hosts, and the reset then deletes the fork's Incus host.

## 11. Track A's fields in the record<a id='track-a'></a>

Implements `episodes.md` §13 (episode record) for Track A.

The episode's file in the episode record, `record.json` in a fork and `episode.json` at fork 0, holds Track A's fields under the key `track_a`, in Track A alone. The key `alarm` holds the step and the arrival time of the first Track A alarm, under its keys `step` and `arrival`, on the clock of the episode's Incus host, or `null`. The keys `K`, `k_n` and `R_n` hold the values of Track A's episodic reward, with `K` and `k_n` `null` in a benign episode, and `k_n` 0 for outcome 3 (`episodes.md` §13, episode record). The key `outcome` holds `1`, `2`, `3` or `4` in an adversarial episode, and `false alarm` or `none` in a benign one (`episodes.md` §13, episode record). Beside `track_a`, the episode's file holds the episode's outcome under the key `outcome` (`episodes.md` §12, terminated and discarded episodes). The outcome is `alarm` when the alarm ended the episode, and `last_stage` when the start of its last stage did. The key `end_cause` of `track_a` holds the episode's end cause: `horizon`, `alarm`, `last_stage` or `simulator_stop`. The end causes `horizon`, `alarm` and `last_stage` take the value of the episode's outcome. A simulator stop gives the end cause `simulator_stop`, with the outcome `terminated`, or `discarded` for a failure of the testbed (`episodes.md` §12, terminated and discarded episodes). A terminal state that the ground-truth evaluator identifies takes its end cause with the evaluator's specification (`episodes.md` §19, open items). In either track, the key `end_reason` under the key `steps` states in prose why the steps ended, for diagnosis. An alarm that arrived after a simulator stop is dropped with the steps after the stop, and `alarm` then holds `null` (`episodes.md` §7, step protocol).

## 12. Query interface<a id='query'></a>

Implements `episodes.md` §8 (query interface), first version.

The competition image of `siem-01` installs the program `/usr/local/bin/siem-read`. The defender runs `siem-read alerts` or `siem-read archives`, with the options `--host NAME` and `--input LOCATION` to select by originating host and input, and `--since TIME` to name the request's start. The host is a record's `agent.name`, and the input is its `location`, the log file or command the Wazuh agent collected it from. `TIME` is an instant in Coordinated Universal Time (UTC), such as `2026-11-12T20:15:05.250000Z`: a date and a time of day joined by `T`, with an optional fraction of a second and the suffix `Z`. The program writes the matching records to its standard output, one JSON object per line as the file holds it, in the file's order, and exits with status 0. A request that the program cannot serve exits with status 2 and a message on standard error. Such a request names an unknown file or option, or a `TIME` that is not in that form or lies after the read on the clock of `siem-01`. When its standard output closes before a read ends, the program exits with status 1 and enters nothing in the record of reads.

The program keeps its state in `/var/lib/siem-read/` on `siem-01`. The state holds a position for each request, the dated file and the byte offset that the request's previous read reached. A request is its output file, host, input and start, with the start taken as an instant to the microsecond, so two spellings of one instant name one request. At the start of step 0, the episode runner runs `siem-read --start --step-0 TIME --step-s SECONDS`, with step 0's instant in UTC in the form that `--since` takes, and the step duration in seconds. The episode runner takes step 0's instant from its own clock, which the containers on the episode's Incus host share. The episode runner runs the option through an `incus exec` of its own into `siem-01`, apart from the step session, as for scan requests (§3, scan requests). The option records each output file's dated file and the offset after its last whole record. The option also records step 0's instant and the step duration, 5 seconds when `--step-s` is absent. The program numbers each read's step from that instant. The episode runner opens the step session before it runs the option. The episode runner sends step 0's decision request once the option has exited with status 0. Any other exit discards the episode as a failure of the testbed (`episodes.md` §12, terminated and discarded episodes), and the episode runner then closes the step session's standard input with no step message. A request without `--since` starts at the recorded offsets. A read made before the option has run exits with status 2, with or without `--since`.

The option takes the offsets a fraction of a second into step 0, once the step session has opened, at fork 0 and in a fork alike. A request with `--since TIME` starts at the first record whose timestamp is at or after `TIME`. A record's timestamp is its key `timestamp`, the instant at which the Wazuh manager processed the record, on the clock of `siem-01`, such as `2026-11-12T20:15:05.217+0000`. The program searches the output file's dated files in the order of their days, and the records of each file in the file's order. The search begins at the earliest dated file whose day is not before the day that holds `TIME`, both days on the clock of `siem-01`. A `TIME` before the security monitoring's first record therefore starts at that record. When the read finds no record at or after `TIME`, the request starts at the end of the current day's file.

When the search begins in the current day's file, which is not compressed, the program may start at a record whose timestamp is more than 300 seconds before `TIME`, and scan forward. The program scans a compressed file from its start. The start found is the same as that of a search from the file's start, provided that the Wazuh manager writes no record more than 300 seconds after its timestamp. Across 1,281,993 records of one day's `archives.json`, no record's timestamp lay more than 1.09 seconds behind that of a record written before it. The records of the same day's `alerts.json` lay wholly in the order of their timestamps.

No record written before step 0 holds a trace of the episode runner's own commands in `siem-01` and the adversary host: the check of the chain's binary, the step session and `siem-read --start`. A living port runs no attack chain and no step session, and an episode's attack chain starts at the onset step, step 6 at the earliest (`episodes.md` §6.3, the living port; §10.3, onset and waits). A read of the history therefore reveals nothing of the episode's type.

The Wazuh manager writes each day's records to a dated file, and `alerts.json` and `archives.json` are second names for the current day's files (`siem.md` §7, retention). A read first reads the rest of the dated file at the request's position, which for the request's first read is its start. The read then reads each later dated file from its first byte, up to the current day's file. The program reads a dated file that the Wazuh manager has compressed in its decompressed form. A read ends at the end of the current day's file as the read finds it, so no read returns a record written after the read. A record that the Wazuh manager is still writing waits for the next read.

Each read appends one JSON object to the record of reads, `/var/lib/siem-read/reads.jsonl`. The object holds the read's step, under the key `step`, computed from the clock of `siem-01` and step 0's instant, and that time, under `time`. The object also holds the request under `request`, with its keys `output`, `host`, `input` and `since`. The key `since` holds the request's start to the microsecond in the form `2026-11-12T20:15:05.250000Z`, or `null` for a request without one. Each dated file with the byte range read is under `ranges`, and the number of records returned under `records`. The record names a dated file by its path relative to `/var/ossec/logs/`, without the suffix `.gz` that compression adds, and counts a byte range in the file's decompressed content. The export copies the record of reads into the episode record with the dated files to which its ranges refer (§10, export).
